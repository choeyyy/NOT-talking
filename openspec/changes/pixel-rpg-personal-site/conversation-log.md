## 技术路线对比（面向「以后要部署云服务器」）

假设：中小规模、你可控、要好看、要权限。

### 路线 A：Next.js 全栈（推荐作为默认思考起点）

```
浏览器 ──▶ Next.js (App Router)
              ├── 页面 + UI（React + Tailwind + shadcn/ui）
              ├── API Routes / Server Actions
              └── Auth（NextAuth / Lucia / Clerk 自建版）
                    │
                    ▼
              PostgreSQL / SQLite
```

| 优点 | 缺点 |
|------|------|
| 前后端一体，部署简单 | 要学 React 生态 |
| SSR/SEO 友好（若有公开页） | 权限中间件要设计清楚 |
| shadcn/ui 容易做出「有设计感」 | |
| Docker + 云服务器很成熟 | |

**权限**：middleware 里按 session 角色拦截路由；页面级用 server component 再查一遍。

### 路线 B：前后端分离（Vue/React SPA + 独立 API）

```
SPA (Vite) ──API──▶ FastAPI / NestJS / Go
                         │
                         ▼
                    PostgreSQL
```

适合：API 要复用、以后可能有 App。代价：部署两个服务、CORS、前端路由权限要自己包一层。

### 路线 C：低代码/快速验证（Supabase / PocketBase + 前端）

```
前端 (Next/Vue) ──▶ Supabase Auth + RLS
                 或 PocketBase（单文件后端）
```

| 优点 | 缺点 |
|------|------|
| 登录、用户表、JWT 开箱即用 | 数据在第三方或要自托管 Supabase |
| Row Level Security 做数据权限 | 「设计感」仍要靠前端 |
| 云服务器可自托管 PocketBase | 复杂业务逻辑可能碰壁 |

适合：**快速验证**「不同用户看不同东西」，再决定是否迁移。

### 路线 D：纯静态 + 外部 Auth 服务

若页面不多、权限简单（如 2 种角色），可以用 Cloudflare Access、Authelia 等在 **反向代理层** 挡路由——应用本身几乎无 auth 代码。但灵活度低，不适合复杂业务。

## 权限模型（建议尽早定）

最常见、也够用的一种：

```
User ──belongs to──▶ Role(s) ──grants──▶ Permission(s)
                                              │
                                              ▼
                                         Route / Action
```

示例角色：

```
guest     → 仅登录页 + 公开页
member    → /dashboard, /profile
editor    → + /content/*
admin     → + /users, /settings
```

**两层防护**（别只靠前端藏菜单）：

1. **路由守卫**：未授权 → 403 或重定向
2. **API 守卫**：每个敏感接口校验 session + 权限

```
用户请求 /admin/users
        │
        ▼
   middleware: role === admin? ──No──▶ redirect /403
        │ Yes
        ▼
   page render + API 再次校验
```

## 核心对象（建议先定这 3 个）

```
┌─────────┐       ┌─────────────────┐       ┌─────────┐
│  User   │──N:M──│  UserPageAccess │──N:M──│  Page   │
└─────────┘       └─────────────────┘       └─────────┘
  email              user_id + page_id         path
  password           (可带 granted_at)         label
  is_admin                                     is_public?
  active
```

| 实体 | 谁 CRUD | 说明 |
|------|---------|------|
| **User** | 仅 admin | 建账号、禁用、改密码 |
| **Page** | 通常**代码注册**，admin 只读 | 站点有哪些「可授权页面」 |
| **UserPageAccess** | admin CRUD | 「用户 A 能访问页面 X」 |

关键点：**Page 不建议让 admin 在后台随意新建路由**（会变成半个 CMS）。更稳的做法是——开发时在代码里注册页面清单，admin 只做 **勾选谁能看**。

```
代码里注册（单一真相源）          管理员后台操作
─────────────────────          ─────────────────
/dashboard      ←──────────    ☑ 用户张三
/projects       ←──────────    ☐ 用户李四
/private/notes  ←──────────    ☑ 用户张三
/admin/*        ← 仅 is_admin  （不进权限矩阵）
```

## 两种角色，别混在一个维度里

```
is_admin = true   →  永远能进 /admin/*，且能 CRUD 用户权限
is_admin = false  →  只能进 UserPageAccess 里勾选的页面 + 公开页
```

不要把 admin 也塞进「页面权限表」里，否则逻辑容易绕：

```
❌ admin 也是 UserPageAccess 里的一条
✅ admin 是独立标志，/admin 路由单独守卫
```

## 管理员后台：权限 CRUD 怎么做得好用

个人站用户少，**矩阵勾选**比「一条条 Permission 记录表单」更直观：

```
              │ 仪表盘 │ 私人笔记 │ 相册 │ 下载区 │
──────────────┼────────┼──────────┼──────┼────────┤
张三          │   ✓    │    ✓     │  ✓   │   ✗    │
李四          │   ✓    │    ✗     │  ✗   │   ✗    │
王五          │   ✗    │    ✓     │  ✓   │   ✓    │
```

对应 CRUD：

| 操作 | 界面 | API 语义 |
|------|------|----------|
| **C** | 勾选一格 | `POST /admin/access { userId, pageId }` |
| **R** | 打开用户详情 / 权限页 | `GET /admin/users/:id/pages` |
| **U** | 改勾选（本质是删+增） | `PUT /admin/users/:id/pages` 批量替换 |
| **D** | 取消勾选 | `DELETE /admin/access { userId, pageId }` |

用户 CRUD 单独一页：`/admin/users`（列表 + 新建 + 禁用 + 重置密码）。


## 技术选型（针对你这个具体需求）

个人站 + 小后台 + 以后要部署云服务器，仍然推荐：

```
Next.js (App Router)
├── 公开页 + 受保护页（同一项目，middleware 分流）
├── /admin 子路由（admin layout + 表格 UI）
├── Auth：Credentials（邮箱密码），session cookie
├── DB：SQLite 起步 → 上云可换 PostgreSQL
└── UI：Tailwind + shadcn/ui（表格、对话框、开关都很好做）
```

为什么合适：

- 个人站要 **设计感**：shadcn 定制空间大
- 权限 CRUD：admin 表格是成熟模式
- 云部署：单 Docker 镜像 + 反向代理即可
- 用户量小：SQLite 完全够用，schema 也简单

**不太建议**此时上 Supabase RLS——你的权限是「页面级」而不是「行级数据」，自建 3 张表更直观。

## 数据表草案（探索用，不是最终实现）

```sql
users
  id, email, password_hash, is_admin, is_active, created_at

pages                    -- 可由 seed/migration 从代码同步
  id, slug, path, label, sort_order, is_public

user_page_access
  user_id, page_id, granted_at
  PRIMARY KEY (user_id, page_id)
```

`pages` 可以：

- **A.** migration seed 固定（改页面要发版）——个人站通常够用  
- **B.** 启动时从 `site-pages.ts` 配置 sync 进 DB——admin 界面永远和代码一致  

B 稍好一点：加新页面只改一处配置，admin 后台自动出现新列。

## 3. 接入 AI：Composer 2.5 + Grok 4.5

这是架构里**最需要先对齐**的一块。

### 要先澄清：这两个模型怎么调用？

| 模型 | 常见可用方式 | 自建站点的现实 |
|------|--------------|----------------|
| **Grok 4.5** | [xAI API](https://x.ai/api) 等 | 有公开 API，后端代理即可 |
| **Composer 2.5** | Cursor 内置 Agent 模型 | **通常没有**给第三方网站直接调用的公开 API |

所以有两种可能：

```
A. 你有内部/统一模型网关（公司 OpenAI-compatible endpoint）
   → 网站只配 base_url + model id：composer-2.5、grok-4.5

B. 没有网关，只有公网 API
   → Grok 走 xAI；Composer 2.5 需要换等价模型或确认 Cursor/内部是否提供 API
```

**实现前建议确认**：Composer 2.5 的 **HTTP endpoint、鉴权方式、model 字符串** 是否已有。没有的话，proposal 里应写「Grok 确定；Composer 待 endpoint 确认或占位」。

```

   ├─────────────────────────▶│  校验登录 + 可选限流          │
   │                          ├───────────────────────────▶│
   │                          │◀───────────────────────────┤
   │◀─────────────────────────┤  SSE 流式返回                 │
   │                          │                            │
   API Key 只在服务端 .env      │
```

## Cursor API 双模型

你已有 Cursor API，Composer 2.5 的接入路径就通了。Grok 4.5 有两种可能：

```
情况 A：Cursor API 同一 endpoint，换 model 参数即可
        composer-2.5  |  grok-4.5

情况 B：Grok 需另走 xAI，Composer 走 Cursor
        → 后端做 model router，对前端仍是一个接口
```

proposal 里可写：**统一 `/api/ai/chat`，内部按 model 路由**；具体 endpoint/model 字符串以你 Cursor 文档为准（实现前抄一份 `.env.example`）。

建议在服务端做映射表，避免前端乱传 model：

```ts
// 概念示意，不是实现
const MODELS = {
  'composer-2.5': { provider: 'cursor', model: '...' },
  'grok-4.5':     { provider: 'cursor', model: '...' }, // 或 xai
}
```

## 视觉方向：像素跑团风

参考气质：**Undertale / Stardew / 经典 JRPG 对话框**，而不是现代 SaaS 仪表盘。

### 设计 tokens（建议）

| 维度 | 方向 |
|------|------|
| **字体** | 像素字体：中文可用 **方舟像素** / **点阵字体**；英文 **Press Start 2P**、**VT323** |
| **配色** | 有限色板：深紫/墨绿背景 + 高饱和强调色（金、红、青）；避免大面积渐变 |
| **边框** | `box-shadow` 阶梯像素边（4px 步进），不用细线圆角卡片 |
| **按钮** | 按下时 `translate(2px,2px)` + 阴影减少，像 FC 按键 |
| **背景** | 平铺像素 tile 或 starfield；动效要克制 |
| **头像** | 方形像素框 + 可选 1px 描边；上传后可 `image-rendering: pixelated` |

### JRPG 对话框范式（全站组件语言）

```
┌──────────────────────────────────────────┐
│ ▼                                        │
│  欢迎来到这片大陆，冒险者。                  │
│  ─────────────────────────────────────   │
│                              [ ▶ 确定 ]  │
└──────────────────────────────────────────┘
```

可用于：登录提示、403「此区域尚未开放」、公告详情、AI 回复气泡。

## 创世主（Admin）界面

admin 不应像普通后台表格，而是**天界控制台 / DM 屏幕**：

```
┌─ 创世主祭坛 ─────────────────────────────────────┐
│ [👤 冒险者名册]  [🗺 区域权限]  [📜 世界公告]      │
├──────────────────────────────────────────────────┤
│  创建新冒险者                                       │
│  ┌────────────────────────────────────────────┐  │
│  │ 名号: [________]  初始区域: [☑酒馆 ☑训练场] │  │
│  └────────────────────────────────────────────┘  │
│  ── 区域权限矩阵（勾选 = 赐予进入权）──            │
│       酒馆   密库   档案室   神谕之间               │
│  张三   ✓     ✓      ✗       ✓                   │
│  李四   ✓     ✗      ✗       ✓                   │
└──────────────────────────────────────────────────┘
```

文案示例：

- 「创建用户」→ **「赋予冒险者身份」**

## 技术实现（探索层，不写代码）

像素风主要是 **CSS + 资产**，不动 auth/RBAC 核心：

```
功能层（已定）                    表现层（新增）
─────────────                    ─────────────
Next.js + middleware      +      像素 UI 组件库（主题化 shadcn）
RBAC + Cursor API         +      像素字体 / sprite / tile 背景
SQLite                    +      可选 8-bit 音效（howler.js）
```

**实现路径：**

| 层级 | 做法 |
|------|------|
| **CSS** | Tailwind 自定义 theme：`pixel-border`、`font-pixel`；`image-rendering: pixelated` |
| **组件** | Dialog / Button / Panel 统一 JRPG 皮肤 |
| **资产** | 少量 PNG sprite（按钮、边框、图标）；可用 [LPC](https://opengameart.org) 类素材 |
| **动效** | CSS step 动画；避免 smooth 圆角 transition |
| **中文像素** | 务必 early 测字体 fallback，避免中文变糊 |

shadcn 仍可用——**换 token 和组件皮肤**，不必换框架。

## 两个需求，其实是两件事

```
┌─────────────────────┐     ┌─────────────────────┐
│   世界地图（导航）    │     │  捏人（角色形象）     │
│   去哪、能进哪些区域  │     │  长什么样、头像展示   │
└──────────┬──────────┘     └──────────┬──────────┘
           │                           │
           └───────────┬───────────────┘
                       ▼
              都服务「跑团个人站」体验
              但技术量和工期差很多
```

| 档位 | 世界地图 | 捏人 | 工期感 |
|------|----------|------|--------|
| **Lite** | 一张像素大地图 + 点击热点跳转 | 选预设立绘（8～16 个） | +小 |
| **Medium（推荐）** | 可交互地图，未解锁区域灰/锁 | 分层捏人（发型/肤色/衣服）合成像素小人 | +中 |
| **Heavy** | 能走动探索的 2D 场景 | 完整像素编辑器 + 地图碰撞 | 接近做游戏 |

个人站 MVP：**Medium 的地图 + Medium 的捏人** 最划算；**Heavy 建议当 V2**，否则很容易盖过 admin/权限/AI 主线。

## 世界地图：网页里完全可行

地图不必是「真游戏」，可以是 **导航壳**，背后仍是你们的路由和权限。

```
                    ┌─────────────────────────────┐
                    │      像素世界地图 /map       │
                    │                             │
                    │    [🏠酒馆]──[📚档案室🔒]    │
                    │       │                     │
                    │    [⚔训练场]──[🧙神谕之间]   │
                    │                             │
                    │         👤 你的小人站在当前区  │
                    └─────────────────────────────┘
                              │
              点击「档案室」──┼── 有权限 → 进入 /archive
                              └── 无权限 → JRPG 弹窗「创世主未开放」
```

### 三种实现路线

**A. 静态图 + 热点（最懒、够用）**

```
一张 pixel map PNG
+ 绝对定位的透明按钮区域
+ 每个区域绑 path + pageId
```

- 优点：快、好做、设计师画一张就行  
- 缺点：难扩展、区域多了不好维护  

**B. DOM/CSS 地图（推荐 MVP）**

```
div 网格 或 flex 布局的「区域块」
+ 像素边框 / sprite 图标
+ 权限决定 class: locked | unlocked | current
```

- 优点：和 Next.js 天然契合，SEO/无障碍好做  
- 缺点：不像「大地图」，更像「区域选择屏」（很多 JRPG 就是这样）

**C. Canvas 引擎（Phaser / PixiJS）**

```
真 2D 场景、缩放、粒子、将来可走路
```

- 优点：最像游戏，以后能进化成 Heavy  
- 缺点：bundle 大、移动端性能、开发量明显上去  

**和权限的绑定（三种做法都一样）：**

```
pages 表里的每个 Page
  → map_x, map_y, map_icon, map_label  （地图上的展示）
  → path                               （点击后跳转）

UserPageAccess
  → 决定地图上该区域是「可点击」还是「锁定/迷雾」
```

登录后默认 landing：**`/map` 世界地图**，比 `/dashboard` 更符合跑团感。

## 捏人：也能做，推荐「分层合成」而不是自由绘画

用户上传照片那种 **不适合** 像素跑团；更合适的是 **LPC 式分层选件**（开源像素人物体系，部件可叠：身体、发型、衣服、配色）。

```
┌─ 角色创建 /profile/character ─────────────────┐
│  ┌────────┐   肤色  (○ ○ ● ○)                  │
│  │ 预览   │   发型  [▼ 短发/长发/…]             │
│  │ 像素小人│   上衣  [▼ …]                      │
│  └────────┘   下装  [▼ …]                      │
│               配色  [主色][辅色]                  │
│                        [ 💾 保存立绘 ]          │
└────────────────────────────────────────────────┘
```

### 数据怎么存

```json
{
  "body": "male_light",
  "hair": "spiky_01",
  "hairColor": "#8B4513",
  "top": "_tunic_blue",
  "bottom": "pants_brown"
}
```

| 字段 | 用途 |
|------|------|
| `character_config` (JSON) | 可再编辑、重新合成 |
| `avatar_url` 或 blob | 列表/地图/AI 旁展示用的小图 |

合成方式：**浏览器 Canvas 把各层 PNG 叠起来 → 导出 32×32 或 64×64**（经典 RPG 尺寸）。

### 捏人档位

| 档位 | 体验 | 工作量 |
|------|------|--------|
| 预设库 | 选 1 张立绘 | 很小 |
| 分层选件（推荐） | 发型/衣服/色板组合 | 中等；资产要整理 |
| 自由像素画 | 用户自己涂 | 大；个人站通常不值 |

**V1 建议：** 2～3 个身体底模 × 若干发型/衣服 × 调色板，组合数已经够「捏」的感觉。

| 项 | 选择 |
|----|------|
| 引擎 | **Phaser 3**（2D 走动 + 碰撞 + Tiled 成熟） |

```

├── 世界地图上看不见 B 的小人            ├── 同上
├── 不能对 B 开聊天框                    ├── 同上
├── 看不见 B 的 id / 名号                ├── 看不见 A 的 id / 名号
└── （建议）展馆里也搜不到/看不到 B        └── 同上
```

## 数据模型：三种做法

### 方案 A：两两「不认识」（边表，最贴你的描述）

```
user_strangers (或 user_visibility)
  user_id
  stranger_user_id      -- 「我不认识谁」
  created_by_admin_id
```

## 第 13 轮

**时间：** Monday, Aug 10, 2026, 5:18 PM (UTC+8)

### 用户

实时沟通要什么技术栈

### 助手

根据 `design.md` 里的 Phase 2 设计，实时沟通可以拆成两块：**在线 presence（地图上人）** 和 **玩家私聊**。推荐栈如下。

## 总体架构

```
浏览器                         你的服务器                    存储
  │                                │                         │
  ├─ /world (Phaser)               │                         │
  │    WS 连接 ──────────────────▶│ WebSocket Server        │
  │    坐标、spawn/despawn         │  + canSee() 过滤广播     │
  │                                │                         │
  ├─ 任意 Tab 聊天 UI               │                         │
  │    WS 收消息 / REST 发消息 ────▶│  Chat API               ├──▶ SQLite/Postgres
  │                                │  (messages 表)          │     (messages 持久化)
  └─ Session Cookie 鉴权            │                         │
```

**原则：** WebSocket 负责「推」；消息落库用 REST 或 WS 都行；**鉴权靠 session**，API Key 不进浏览器。

---

## 推荐技术栈（与 proposal 一致）

| 层级 | 推荐 | 作用 |
|------|------|------|
| **全栈框架** | Next.js 14+ (App Router) | 页面、REST API、session |
| **WebSocket** | **`ws`** 或 **Socket.io** | 长连接、presence、聊天推送 |
| **WS 挂载** | Custom Server 或独立 `ws` 进程 | Next 默认不自带 WS，需自定义 server 或 sidecar |
| **鉴权** | 现有 **httpOnly session** | 握手时校验 cookie / token |
| **数据库** | SQLite → Postgres | `messages` 表持久化 DM |
| **ORM** | Drizzle / Prisma | 存聊天记录 |
| **地图** | Phaser 3 | 只在前端渲染多人 sprite |
| **反向代理** | Nginx / Caddy | **必须**配置 `Upgrade` 头，否则 WS 不通 |

### 为什么选 `ws` vs Socket.io

```
ws / 原生 WebSocket          Socket.io
────────────────────         ────────────────────
轻、协议简单                  自带重连、房间、广播 helper
自己写心跳/重连               客户端略大
个人站人数少足够               开发更快，文档多
```

个人站、<30 人在线：**`ws` 够用**；想少写重连/房间逻辑：**Socket.io** 更省事。

## 实时层要实现的协议（概念）

### 1. Presence（只在 `/world` Tab）

```typescript
// 客户端 → 服务端
{ type: "join_world" }
{ type: "move", x, y, direction }

// 服务端 → 客户端（已按 canSee 过滤）
{ type: "spawn", userId, name, avatarUrl, x, y }
{ type: "update", userId, x, y }
{ type: "despawn", userId }
```

- 频率：坐标 **10～20Hz 节流**
- 心跳：**3～5 秒** 无响应则 despawn
- 过滤：服务端对每个连接单独算「能看见谁」

### 2. 聊天

```typescript
// 发消息（REST 更简单）
POST /api/chat/messages { toUserId, body }
  → 校验 canSee(sender, to)
  → 写入 messages 表
  → WS 推给在线收件人

// 或全程 WS
{ type: "chat", toUserId, body }
```

**推荐：** **REST 发 + WS 推**——发失败好处理、易落库；在线用户即时收到。

## 实现要点：`canSend()` vs `canSee()`

```typescript
function canSend(from, to) {
```

## 继续讨论：几个待拍板点

### 1. 35% 是否合适？

| 倾向 | 概率 | 体验 |
|------|------|------|
| 稀缺感 | 15–20% | 药水是「大奖」，觉醒有仪式感 |
| **当前默认** | **35%** | 大约每 3 次大成功 1 瓶，中等肝度 |
| 慷慨 | 50%+ | 很快人人有 Agent 造物，差异化变弱 |

个人倾向：**先 35% 上线**，创世主后台可调；若玩家人数少、副本短，再降到 25%。

### 2. 「大成功」怎么定义？

目前 spec 只写了 ending tier，**还没钉死**和 d100 检定的关系。两种常见做法：

- **A. 结局驱动**：剧本结局节点标 `tier: crit_success`（跑团 GM 叙事感强）
- **B. 检定驱动**：某次 d100 ≤5 或 ≥96 才解锁 crit_success 结局分支

你更想要哪种？还是 **A 为主 + 少数副本用 B**？

### 3. 觉醒后 vs 随机 `phrases[]`

赋活造物在家里的表现：

- **替换**：有 binding 就只走 Agent 对话，不再随机气泡（省 token、人设一致）
- **并存**： idle 仍随机 phrases，点进才 chat（更「活物」、更费 API）
- **混合（推荐）**：未互动时低频 phrases；玩家点开后切 Agent chat

### 4. 复活台能卖「已赋活」造物吗？

tasks 里倾向 **禁止**（有 binding 的 creation 不可估价出售）。否则玩家可能为了复活费「献祭」自己养出来的 Agent。若同意禁止，需要在 `world-revival` spec 补一条。

### 5. 之子赠金 vs 药水经济

之子能赠金币，但 **不应**直接赠药水（否则绕过副本）。药水只来自：crit 掉落、剧本节点、创世主 admin（可选）。

## 解法：Runtime Dungeon Registry（运行时剧本注册表）

```
工程精灵 → dungeon_script_drafts（JSON）
              ↓ 造物主对话同意
         Publish API
              ↓
    dungeon_scripts（live）+ dungeon_entrances? + 公告
              ↓ cache invalidate（进程不重启）
         下一局 /dungeon/[id] 立刻可玩
```

| 层 | 是什么 | 谁用 |
|----|--------|------|
| **Bootstrap** | 仓库里示例 JSON，migration seed 一条 | 首启有个样例本 |
| **Runtime** | DB `dungeon_scripts` + `dungeon_entrances` | 精灵发布、热更、工程精灵 |

**工程精灵边界：** 只调服务端 API 写 draft JSON，**不改** `.ts`、**不**出 migration、**不**触发 deploy。

**热更安全：** 进行中的 run 开局时 **钉住** `script_version`；新 publish 只影响 **新开局**。

**大世界入口：** Tiled 静态入口 + DB 动态入口 **合并**；精灵新本可以只在 DB 挂入口，不用改地图资产。
